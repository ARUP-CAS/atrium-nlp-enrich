## Breaks advertised behavior

**1. `num_keywords` is silently ignored — it never reaches the pipeline.** `/enrich`, `/enrich_text`, and `/jobs` all accept it, validate it (1–100), and thread it through `_run_pipeline_sync` → `PipelineManager.enrich(num_keywords=...)`. Then it dead-ends: `enrich()` builds `cmd = [..., "--kw", "--kw-method", kw_method]` with no count, and `run_pipeline.py` has no `-n`/`--num-keywords` option at all, so its keyword command (`-i -m -o -d --paradata-dir`) never forwards one. Every request gets the hardcoded default of 20 from `kw_config.txt`. Since you only call `run_pipeline.py`, the fix is at both ends: add `-n/--num-keywords` to `run_pipeline.py`'s argparse and append `"-n", str(args.num_keywords)` to the `keywords.py` command, then have `enrich()` pass it through:
```python
cmd.extend(["--kw", "--kw-method", kw_method, "--num-keywords", str(num_keywords)])
```

**2. `format=zip` leaks the entire workspace on every request.** In `_run_enrichment`, the `finally` only cleans up when `fmt != "zip"`. The zip branch returns a `FileResponse` pointing inside `result.workspace` and nothing ever deletes it — no background task, no retention check. Each zip download leaves a workspace plus the archive on disk forever. Attach cleanup to the response instead of skipping it: `FileResponse(..., background=BackgroundTask(PipelineManager.cleanup, result))` (still honoring `API_KEEP_WORKSPACES`).

**3. KeyBERT warmup can hard-crash startup instead of degrading.** `_get_keybert_model` calls `sys.exit(1)` on model-load failure, which raises `SystemExit` — a `BaseException`, not `Exception`. `PipelineManager.warmup`'s `except Exception` can't catch it, so it propagates out of `run_in_executor` and fails the lifespan startup. The Docker `nlp-api` service never prefetches the model (only `setup_api_service.sh` does), so the first container start downloads `paraphrase-multilingual-MiniLM-L12-v2`; if HF is unreachable, the service refuses to start rather than starting and degrading to yake as the `except` intends. Either catch `BaseException` in `warmup`, or stop calling `sys.exit` inside `_get_keybert_model` now that it's reused as a server component — raise instead.

**4. The keybert→yake degradation only fires for *missing deps*, not runtime keybert failure.** The preflight in `run_pipeline.py` runs before the stages, so a missing keybert returns 3 → `KeywordPreflightError` → retry with yake. But in the actual deployment keybert/sentence-transformers/torch are all in `requirements.txt`, so the preflight passes and any real keybert problem surfaces at model-load time as `keywords.py` `sys.exit(1)` → `run_pipeline.py` returns 1 → `enrich()` maps it to `PipelineError(502)`. So a runtime keybert failure (a) does not degrade and (b) fails the whole request with 502 even though stages 1–4 — the actual TEITOK — already succeeded. Exit 1 also conflates "empty run" with "keybert crashed," so they can't be told apart. Note that `test_enrich_keybert_degrades_to_yake` only exercises the rc=3 path, so it gives false confidence that degradation is robust.

## Stubbed / non-functional

**5. Both web frontends are inert.** `service/frontend/script.js` and `service/frontend-lindat/script.js` are empty files, but both `index.html` pages rely on `<script src="script.js">` to submit `#enrichForm`. The "Run Enrichment" button does nothing (the form has no `action` and no JS handler). Separately, both inputs advertise `accept=".csv,.xlsx,.txt,.zip"`, but `normalize_upload` only handles csv/txt/xlsx and rejects `.zip` with 422 — so even once the JS exists, the `.zip` option is a dead promise (consistent with open question #3, but the HTML shouldn't offer it yet).

## Consistency & robustness

**6. `/jobs` skips parameter validation.** Sync `/enrich` runs `_validate_params` (422 on bad `kw_method`/`lang`/`num_keywords`), but `submit_job` → `_run_job_background` → `_run_enrichment` never validates. A bad `kw_method` only blows up inside `enrich()` as a `ValueError`, caught by the generic handler and surfaced as a failed job rather than a clean 422 at submission. Validate in `submit_job` before creating the task.

**7. `DELETE /jobs/{id}` targets the wrong directory.** `cleanup_job` does `rmtree(_API_JOBS_ROOT / job_id)` using the `Job.job_id`, but the workspace was created under a *different* uuid inside `PipelineManager.enrich()` (`job_id = uuid.uuid4().hex`). So that rmtree hits a path that never existed; the only effective line is `del _jobs[job_id]`. It doesn't actually leak (the real workspace is already removed by `_run_enrichment`'s finally), but it's dead code reflecting a wrong assumption that `Job.job_id` maps to a workspace.

**8. Warmup doesn't actually warm the request path.** Because keyword extraction runs in a subprocess (`run_pipeline.py` → `keywords.py`), the model warmed in-process at startup is never reused — each request's subprocess reloads the sentence-transformer into RAM (~1–3s for MiniLM). Warmup only pre-populates the HF *disk* cache, saving the one-time download, not the per-request load. That's inherent to the "only call `run_pipeline.py`" design, but it means the strategy's "first request doesn't pay model load" isn't true for in-RAM latency — worth documenting honestly, or reconsidering if latency matters for the sync endpoint.

**9. `_is_empty_failure`'s `skipped >= total` heuristic is wrong for fresh workspaces.** It treats "all files skipped" as a legitimate resume, which is right for re-runs but wrong per-request: in a fresh workspace a skip (e.g. `build_manifest_row.py` failing on empty-text input) is a genuine failure that gets masked, and the run continues to later stages. Your no-TEITOK backstop in `enrich()` catches the end result (502), so it isn't exploitable, but the empty-run guard is effectively bypassed for the API.

**10. `_jobs` grows unbounded** — completed jobs persist in memory until an explicit DELETE that most clients won't send. Fine for a demo, a leak for a long-lived service; add a TTL/eviction (Phase 3).

## Documented spec gaps (lower priority)

**11. `/health` doesn't probe LINDAT** — only `run_pipeline.py --dry-run` (config validity). The strategy spec'd config validity *plus* LINDAT reachability; the README is honest about the reduced scope, so this is a known partial rather than a silent miss.

**12. `lang` is a dead parameter** — validated and threaded but never passed to the pipeline (`enrich()` doesn't even take it). Harmless while `_ALLOWED_LANG=("cs",)`, but it'll silently no-op the moment another language is added, same root cause as `num_keywords`.

**13. `StaticFiles(directory="service/frontend")` is CWD-coupled** — it works under `setup_api_service.sh` and the Docker `api` target (both run from the repo root) and under pytest, but it'll raise at import if launched elsewhere. Anchoring to `_SERVICE_DIR` would make it robust.

Commit d950e1d state:

**1. Missing `nlp-api` service in `docker-compose.gpu.yaml**

* **Strategy Expectation:** The strategy states: *"GPU via existing `docker-compose.gpu.yaml` (KeyBERT auto-detects CUDA)."*
* **Implementation Issue:** The `docker-compose.gpu.yaml` file was not updated to include the new `nlp-api` service. It only specifies NVIDIA driver reservations for the `nlp` and `nlp-llm` services.
* **Impact:** If a user deploys the API using `docker compose -f docker-compose.yaml -f docker-compose.gpu.yaml --profile api up`, the `nlp-api` service will fail to inherit the GPU reservations. Consequently, the KeyBERT extraction model will be forced to run on the CPU inside the container.

**2. Missing `device` field in the `GET /info` endpoint**

* **Strategy Expectation:** Section 2 (API surface) explicitly states that the `/info` endpoint should return: *"stage plan, pinned UDPipe/NameTag models, available kw methods + default, limits, **device**"* to indicate the hardware execution context.
* **Implementation Issue:** In `service/api.py`, the `info()` function accurately maps the stage plan, models, keyword methods, and limits, but completely omits the `device` key from the returned JSON dictionary.

**(Note on Phase 0 patch implementation):** The groundwork patch described in the strategy (passing `-i <OUTPUT_DIR>/UDP` to the keyword stage so it doesn't fail on relocated workspaces) was correctly executed in `run_pipeline.py` (line 389), fixing the CLI correctness issue exactly as planned. All other specified parameters, including the `"llm": null` forward-compatibility flag, file normalization, and async `uvicorn` lifespan handling, perfectly match the design.

### Current state review: 

**Issue #8: Add API Service**
The implementation of the FastAPI service wrapper brings the repository to a highly functional, deployable state. The codebase now cleanly abstracts the core shell scripts (`manifest`, `udp`, `nt`, `stats`) into accessible endpoints within `service/api.py`. It provides both synchronous processing (`/enrich`) and background task queues (`/jobs`) with a built-in semaphore to safely limit concurrent execution. Because the underlying categorization algorithm operates on strict quality-score thresholds rather than a cumulative penalty system, the API is highly efficient—it rapidly drops noisy or purely administrative lines early in the request lifecycle. This strict filtering safeguards the service from queue congestion and VRAM bottlenecks when executing the heavier LLM semantic enrichment stages.

**Issue #9: TEITOK Output Image Files Dependence Handling**
The source code addresses the facsimile alignment problem comprehensively. The standalone `fix_teitok_bboxes.py` script provides a direct mechanism to recalculate bounding boxes across entire directories using specific `dx`/`dy` shifts and `sx`/`sy` scale multipliers. Crucially, this capability is also smartly integrated into the live API via the `/rescale` endpoint. By automatically detecting the source dimensions and applying pure XML coordinate transformations, the codebase ensures that the TEITOK NLP annotations maintain perfect visual alignment over the page images, regardless of downstream resizing or cropping in the web viewer.

**Issue #10: Flexiconv-Supported Input Options**
The pipeline has successfully expanded its ingestion funnel to accommodate arbitrary text-containing formats. The `api_flexiconv.sh` script actively scans input directories and uses a regex pattern mapped to allowed extensions (via the `$FLEXICONV_FORMATS` variable) to route supported files through the `api_util/flexiconv_convert.py` wrapper. This establishes a clean, robust pre-processing hook that standardizes diverse raw inputs into the required TEITOK XML standard before they ever enter the UDPipe or NameTag components, keeping the core pipeline logic neatly unified.
