NameTag 3 model training for the domain-specific entities. Example: https://huggingface.co/alexbrandsen/ArchaeoBERT-NER

An English BERT model for Named Entity Recognition in the Archaeology domain, which is the `bert-base-cased-archaeo` model finetuned for NER, targeting the following entities:

- Time periods (`PER`)
- Places (`LOC`)
- Artefacts (`ART`)
- Contexts (`CON`)
- Materials (`MAT`)
- Species (`SPE`)

A set of new entities is to be defined (flat or nested)
- **flat**: several separate NE types
- **nested**: several major NE types with multiple subtypes of NE in each

Then a dataset of text should be annotated with O-I-B labels. Example sentence at the beginning of a document: 

```
-DOCSTART-	O

John	B-PER
loves	O
Mary	B-PER
.	O

Mary	B-PER
found	O
bronze	B-ART|B-MAT
vessel	I-ART
.	O

```
Where **O** - ignored unimportant tokens, **B-** refers to the first token of NE, and **I-** stands for the next words of NEs.

Draft of the suggested domain-specific NEs from the [ArchaeoBERT model guidelines](https://github.com/athena-ilsp/atrium-csd-ner/blob/b51e78f87a8f9d10f8cddeb2779a0f453cbdf828/docs/archaeobert_ner_gudelines_mt_translation.md ):

- **ARTEFACT** -> Artefacts: Objects found in the ground, ranging from small items like pollen to large ones like canoes. 
	 - Includes building-related objects (e.g. "_beams_", "_planks_", "_beams_") and general concepts like "_waste_" and "_pottery_". 
	 - However, do not annotate overly general categories such as "_artefact_",  "_find material_", "_finds_" find complexes, or "_archeobotanical material_". 
	 - When a descriptive adjective is present, include it (e.g., "_burnt wattle and daub_", "_carbonized wood_", "_rough-walled sherd_") unless the adjective refers to a material (e.g., "_metal household goods_"). 
	 - Natural finds like "iron ore" and "index fossils" are also included. Examples: "_Iron Age shards_", "_Rim of a smooth-walled jug_", "_Pottery concentrations_".

- **PERIOD** -> Time Periods: This category encompasses dates and periods. 
	 - When a date includes a day/month, only annotate the year (e.g., "_2012_" from "_12 december 2012_" (December 12, 2012)).
	 - For time spans with multiple years, include surrounding words (e.g., "_between approx. 1700 and 1850_" & "_from 300 to 100 BC_"). 
	 - Annotate complete time periods (e.g., "_Late Medieval_" "_early 14th century_" "_last quarter of the 15th century_"). 
	 - If words like "_after_", "_before_", "_in the course of_", "_circa_", "_approximately_" precede a time period, do not include them in the annotation (e.g., only "_12th century_" from "_before the 12th century_").
	 -  Do not annotate "_around_", only the year/period following it (e.g., "_around 1100_" becomes "_1100_"). 
	 - If a time period is followed by a year in parentheses, annotate them separately (e.g., "_Middle Ages (500-1500 AD)_"). 
	 - Include years in references (e.g., "_(Smit, 2004)_" in the running text and in the bibliography references). 
	 - Do not annotate years in codes (e.g., "_Rapport 2009-61 ARC_"). 
	 - Do not annotate the article, so in "_The Late Middle Ages_", do not annotate "_the_" (but in "_First half of the 19th century_", annotate everything including "_of the_"). Include "_time_" and "_period_" for terms such as "_Carolingian period_", "_Medieval period_".
	 -  Also annotate words denoting a period, such as "_the Carolingian Empire_" and "_Roman law_". 
	 - For dendrochronological dating, annotate the years plus uncertainty, not the season (e.g., "_spring/summer 1478 and 1483 +6_"). 
	 - Also consider more general time periods such as "_historical time_", "_recent_", "_(pre-)historic_". 
	 - Do not include the word 'period' (e.g., "_Period Late Neolithic_" becomes "_Late Neolithic_"). 
	 - Also include years in references (e.g., "_Van As 2010_", "_Smit 2000b_").
	 - Do not include relative periods such as "_Later periods_". 
	 - Also include things like _"600 years ago_"). 
	 - Annotate ABR period codes as separate annotations: "_Neolithic (NEO_)".

- **LOCATION** -> Locations and places: This includes municipalities, provinces, and countries. 
	 - For municipalities, annotate only the place name (e.g., "_Municipality Zutphen_" becomes Zutphen). Annotate full addresses, for example "_P.O. Box 12, 1234NN, Leiden_" and "_Steenstraat 34, Groningen_". Do not annotate "_Dutch archaeologists_" or "_Amsterdam organization_". 
	 - Do not include directions in your annotations (e.g., "_Northern France_", "_Southern Netherlands_"). Unless the direction is part of the place name: "_North Holland_". 
	 - Do not annotate general place designations such as "_the Dutch coastal area_". But do annotate things like "_University of Amsterdam_". 
	 - Do not annotate adjectives indicating a place, such as "_Zutphen castle_", "_Dutch part_", "_German monastery_". 
	 - Do not annotate (highways), rivers, seas, lakes, canals, etc.. 
	 - Do not annotate coordinates. 
	 - If the word 'at/in' is used, include it in one annotation (e.g., "_Valtherweg in Exloo_"). 
	 - Do not annotate abbreviations for provinces, such as "_NH_" (North Holland). 
	 - If 'at/in' is present, also annotate the part before it (e.g., "_Kastanjestraat in Hoorn_", "_Ankeveen polder in Ankeveen_").

- **CONTEXT** -> Contexts: Human-made features that are not artefacts and can generally contain artefacts. 
	 - This includes features like "_cesspit_", "_moat_", "_granary_", "_ditch_", "_ring fort_", "_burial mound_", etc.. 
	 - Also annotate features even if no finds were present (e.g., "_rampart_" or "_wall remains_"). 
	 - Do not annotate natural contexts, for example "_peat layer_", "_cover sand_", "beach ridge", "_dune_" or "_polder vague soils_". 
	 - Do not annotate ground types, for example "_sand_", "_clay_", "_peat_", "_clay layer_", "_clayey sand_".
	 -  Do not annotate modern contexts, such as "_found in the office basement_", where "_basement_" is a modern context. 
	 - Do not annotate overly general contexts such as "_buildings_", "_monument_", "_trace cluster_". 
	 - Do not annotate general designations for traces such as "_disturbances_", "_traces_", "_settlement traces_", "_settlement area_". 
	 - Adjectives can be skipped: "_Shallow postholes_" becomes "_postholes_", "_Iron Age traces_" becomes "_traces_".

- **MATERIAL** -> Materials: These are what an artefact is made of. 
	 - Only annotate materials when they refer to the material of an artefact. So, only "_flint axe_" & "_arrowhead made of bone_", not "_the glass from this excavation_" (that is an artefact). The same applies to, for example, "_The large amount of pottery and glass" and "worked pieces of flint_"; annotate these as artefacts as well. 
	 - Architectural terms for materials can be annotated (e.g., "_the brick wall_" or "_constructed in brick_"). 
	 - Annotate modern materials: "_Concrete garage_". 
	 - Do not annotate adjectives modifying materials (e.g., "_molten bronze_" becomes "_bronze_", "_Oak wood_" becomes "_wood_").

- **SPECIES** -> (Animal and Plant) Species: 
	 - Remember to include humans as a species; "_human bones_" (annotate "_bones_" as artefact). But, for example, do not annotate "_the human_" & "_human influence_". 
	 - For cases like "_cattle skull_", annotate the whole word as an artefact. 
	 - If a Latin species name is followed by a English one, annotate them separately: "_dwarf birch_".

**General Rules:**

* Do not annotate articles (unless they are in the middle of an annotation). So, for example, "_de bijl_" (the axe) and "_de 2e eeuw_" (the 2nd century) (annotate only "_bijl_" and "_2e eeuw_") but "_Eerste helft van de 19e eeuw_" (First half of the 19th century).
* If something is in parentheses before or after an entity, include it if it belongs to the entity ; for example "_(laat) middeleeuws_" ((late) medieval) & "_wal(len)_" (rampart(s)).
* If "_of_" (or) is used to indicate multiple possibilities, annotate the possibilities separately: "_eind van de 11e of begin van de 12e_" (end of the 11th or beginning of the 12th).
* Do not annotate quantity words, such as "_enkele graven_" (some graves), "_een paar schrabbers_" (a few scrapers).

To effectively synthesize the broad, general-domain entity recognition capabilities of the Czech Named Entity Corpus 2.0 (CNEC 2.0) with the highly specialized, domain-specific requirements of the ATRIUM archaeological framework, their taxonomic philosophies must be structurally aligned.

CNEC 2.0 employs a distinct two-level hierarchy consisting of broad supertypes (denoted by capital letters, such as P for Persons, G for Geographical, I for Institutions) and granular two-letter subtypes (e.g., `pf` for first name, `gu` for city). Conversely, the ATRIUM framework relies on six explicit, flat archaeological entities: `ARTEFACT`, `PERIOD`, `LOCATION`, `CONTEXT`, `MATERIAL`, and `SPECIES`.

By mapping the ATRIUM entities directly into the CNEC 2.0 two-level architecture, a unified, multitagset model capable of nested Seq2Seq extraction can be efficiently trained.

### Proposed Merged Taxonomic Hierarchy

The following table outlines a unified schema that preserves the historical breadth of CNEC 2.0 while introducing the strict semantic boundaries required for archaeological excavation extraction.

| CNEC Supertype | Merged Subtype Code | Semantic Definition | Alignment & Rules |
| --- | --- | --- | --- |
| **P** (Persons) | `pf` / `ps` | First names, surnames. | Retains standard CNEC logic. Explicitly excludes biological mentions of humanity or human remains, which must be routed to the Species category. |
| **I** (Institutions) | `in` | Academic, corporate, or administrative bodies. | Retains standard CNEC logic for extracting entities like funding bodies or universities. |
| **G** (Geographical) | `gl` (Location) | Administrative boundaries, coordinates, postal addresses. | Maps to ATRIUM's `LOCATION`. Excludes natural regions or cardinal directions unless legally part of a proper noun. |
| **G** (Geographical) | `gc` (Context) | Anthropogenic structures, cuts, and spatial anomalies. | Maps to ATRIUM's `CONTEXT`. Captures features like moats and postholes, but explicitly excludes natural stratigraphy and soil classifications. |
| **G** (Geographical) | `gh` (Natural) | Rivers, lakes, natural geological formations. | Retains CNEC logic to capture natural topographies. This provides an outlet for natural features that ATRIUM explicitly ignores, preventing model confusion. |
| **T** (Temporal) | `tp` (Period) | Cultural epochs, relative spans, and ABR period codes. | Maps to ATRIUM's `PERIOD`. Forces the exclusion of preceding relative temporal prepositions (e.g., "circa" or "after"). |
| **T** (Temporal) | `ty` (Exact Date) | Absolute calendrical dates and scientific dating spans. | Integrates CNEC's precise date logic to parse complex sequences, such as dendrochronological strings. |
| **A** (Artifacts/Objects) | `aa` (Artefact) | Portable/non-portable material culture and physical finds. | Maps to ATRIUM's `ARTEFACT`. Crucially includes physical condition-based adjectives (e.g., "burnt wattle") directly within the span. |
| **A** (Artifacts/Objects) | `am` (Material) | Raw chemical or biological substances. | Maps to ATRIUM's `MATERIAL`. Excludes material nouns acting linguistically as metonyms for the complete object. |
| **S** (Biological) | `sp` (Species) | Plants, animals, and hominid organisms. | Maps to ATRIUM's `SPECIES`. This is a newly introduced supertype to capture zooarchaeological and archaeobotanical data. |
| **N** (Metrics) | `nm` | Numbers, measurements, trench dimensions. | Retains standard CNEC logic, which is highly critical for tracking spatial and statistical data in technical reports. |
| **C** (Bibliographic) | `cb` | Inline literature citations. | Retains standard CNEC logic for indexing academic references. |

### Strategic Implementation Notes

To operationalize this merged schema utilizing the NameTag 3 framework, several specific structural modifications to the codebase and training parameters are required:

1. **Explicit Tagset Registration:** The system developer must manually extend the `TAGSETS` dictionary within the `nametag3_dataset.py` source code to globally register these new two-letter subtypes alongside their corresponding IOB2 prefixes (e.g., `B-gc`, `I-gc`).

2. **Generative Decoding Architecture:** Because categories like `sp` (`SPECIES`) and `aa` (`ARTEFACT`) frequently overlap in archaeological text (e.g., successfully parsing "human" from within the broader entity boundary of "human bones"), configuring the model with the `--decoding=seq2seq` command-line parameter is mathematically mandated. A flat linear classifier will immediately fail on these overlapping spans.

3. **Rigorous IOB2 Serialization:** All legacy CNEC data and new ATRIUM vertical files must be programmatically standardized strictly to the IOB2 format using internal preprocessing scripts (like `iob_to_iob2.py`) to prevent cross-entropy loss instability during gradient calculation.

## Further develop strategy in brief:

### **Executive Overview**

The integration of advanced NLP into archaeological data processing is crucial for transitioning raw OCR outputs into structured, semantically enriched formats. General-purpose models fail to capture the deep lexical specificity of archaeological discourse. To solve this, the pipeline synthesizes a domain-specific foundation model (**ArchaeoBERT**) with the multitagset, highly scalable extraction capabilities of the **NameTag 3** framework, ultimately mapping a highly specific archaeological taxonomy into the robust hierarchical structure of **CNEC 2.0**.

### **1. Foundation Model: ArchaeoBERT**

The extraction quality relies heavily on the underlying vector representations. ArchaeoBERT provides this domain-adapted baseline.
 * **Architecture:** Fine-tuned over the bert-base-cased model. Casing is fundamentally retained because capitalization delineates semantic boundaries in technical reporting (e.g., "Early Bronze Age" vs. "early artifacts").
 * **Training Corpus:** Continually pre-trained on ~44,000 documents (264 million tokens) from the Archaeology Data Service (ADS).
 * **Objective:** Optimized via Masked Language Modeling to learn the precise distributional semantics of niche terminology (e.g., stratigraphy, postholes).

### **2. Extraction Framework: NameTag 3**

NameTag 3 maps the dense representations from ArchaeoBERT into classified token sequences, supporting complex, overlapping annotations through distinct decoding paradigms:
 * **Classification Head (Flat NER):** Employs a linear layer for linear, non-overlapping entities (standard CoNLL format).
 * **Seq2Seq Decoding Head (Nested NER):** Utilizes generative sequence-to-sequence extraction to handle overlapping spans. This is **mandatory** for archaeology where entities nest (e.g., parsing the SPECIES "human" from within the ARTEFACT "human bones").
 * **Multitagset Alignment:** Allows simultaneous, parallel training on disparate corpora (e.g., broad historical text + niche archaeology text). The model learns to route predictive outputs based on the specific tagset invoked during inference.

### **3. Unified ATRIUM & CNEC 2.0 Taxonomy**

To balance highly specialized archaeological extraction with broad historical context, the flat six-entity ATRIUM taxonomy is merged into the two-level hierarchical supertype/subtype schema of CNEC 2.0.

| Unified Subtype | Entity Scope & Strict Boundaries |
| :--- | :--- |
| **Artefact (aa)** | Physical/material culture. **Includes** physical condition adjectives (e.g., "burnt wattle"). **Excludes** broad hypernyms ("finds") and metonyms. |
| **Period (tp / ty)** | Cultural epochs (tp) and absolute scientific dates (ty). **Includes** internal articles. **Excludes** relative temporal prepositions ("circa", "after"). |
| **Location (gl)** | Administrative and geospatial boundaries. **Excludes** natural topographies or cardinal directions (unless legally part of a proper noun). |
| **Context (gc)** | Anthropogenic structures, cuts, or spatial anomalies (e.g., moats, postholes). **Excludes** natural stratigraphy or modern architectural intrusions. |
| **Material (am)** | Raw chemical/biological substances composing an artefact. **Excludes** material nouns functioning as the complete object. |
| **Species (sp)** | Plants, animals, and hominid organisms. Delineated strictly from resulting physical artifacts. |
| *Auxiliary Entities* | Retains CNEC standards for Institutions (in), Natural Geography (gh), Metrics (nm), and Bibliographic citations (cb) to manage non-archaeological spans and prevent model confusion. | <br> ### **4. Data Serialization: IOB2 Encoding** <br> For NameTag 3 to ingest the data without cross-entropy loss instability, textual data must be programmatically transposed into strict **IOB2 vertical files**. <br> * **Structure:** Each token occupies a single line, paired with its label, separated *only* by a tab (\t). Multiple labels for nested entities are concatenated with a pipe (|).

 * **Context Boundaries:** Blank lines reset the transformer's attention window for sentence limits. Document-level context is explicitly maintained using the -DOCSTART- flag.
 * **IOB2 Logic:** The B- (Beginning) prefix is mathematically required to separate contiguous entities of the exact same class, preventing the model from blending distinct objects (e.g., B-ART I-ART B-ART instead of an unbroken I-ART chain).


### **5. Implementation & Training Pipeline**

Executing the domain-specific adaptation requires precise codebase modifications and strategic hyperparameter tuning on GPU clusters.


**Phase 1: Codebase Modification**
 * The standard NameTag 3 source code (nametag3_dataset.py) must be manually modified to globally register the newly mapped two-letter subtypes (e.g., B-gc, I-gc) within the TAGSETS dictionary. Failure to do so will cause immediate compilation failure.


**Phase 2: Execution & Hyperparameters**
 * The training script (nametag3.py) is executed with strict parameters. Crucially:
   * --context_type="split_document": Forces the model to utilize -DOCSTART- flags to maintain coreference memory across paragraph boundaries.
   * --decoding="seq2seq": Must be invoked to handle the overlapping nature of the merged CNEC/ATRIUM taxonomy.
   * --hf_plm="alexbrandsen/ArchaeoBERT": Binds the foundation model.
   * --batch_size=4 & --learning_rate=2e-5: Constrained parameters to optimize GPU memory and prevent catastrophic forgetting of the pre-trained weights.


**Phase 3: Server Deployment**
 * Once trained, the resulting weights are deployed via the REST API (nametag3_server.py).
 * The multitagset architecture allows the server to load the underlying neural network into memory once, but serve it under multiple dynamic aliases. End-users or automated Web Annotation pipelines can query specific endpoints to receive either generic historical (conll) or highly specialized archaeological (archaeo) JSON outputs from the exact same model.

## Validation & correction of the proposed CNEC 2.0 ↔ ATRIUM alignment by Opus 4.8 Max Code

*Cross-checked against the deployed `CNEC_TYPE_MAP` (`api_util/summarize_nt_udp.py`), the NameTag 3 source (`nametag3.py`, `nametag3_dataset.py`), the CNEC 2.0 hierarchy, and the ArchaeoBERT model card.*

**TL;DR** — the NameTag 3 *mechanics* are right, but the entity-code mapping and the alignment *strategy* need fixing. NameTag 3 multitagset keeps each tagset's labels separate via output masking, so we should add a **separate, newly-defined `archaeo` tagset** (proposed below), not remap archaeology into CNEC two-letter codes. And since ArchaeoBERT is English, we reuse its *guidelines*, not its *weights*, for our Czech/multilingual model.

### Confirmed ✅
- Multitagset training (NameTag 3.1+); `--decoding=seq2seq` for nested vs `classification` for flat — seq2seq is justified, since `bronze vessel → B-ART|B-MAT` is a nested span.
- Real flags: `--context_type=split_document` (the default), `--hf_plm`, `--batch_size`, `--learning_rate`, `--train_data`, `--tagsets`.
- `TAGSETS` dict in `nametag3_dataset.py` is hard-coded → adding a tagset means editing it.
- IOB2 vertical format (token⇥label, `|` for nested, `-DOCSTART-`, blank-line sentence breaks) is correct.
- ArchaeoBERT facts: English `bert-base-cased`, ~44k docs / 264M tokens (ADS); labels `ART/PER/LOC/CON/MAT/SPE`.

### Problems detected ❌

**1. Most mapped CNEC codes collide with existing meanings or don't exist.**

| Proposed | Claimed as | Actual CNEC 2.0 meaning |
|---|---|---|
| `gl` | Location | nature/landscape (mountain/river) — **collision** |
| `gc` | Context | states/provinces — **collision** |
| `gh` | Natural | hydronym (water bodies) — real but narrow |
| `ty` | Exact date | year — ✅ ok |
| `pf`/`ps` | first/surname | ✅ ok |
| `tp` | Period | **does not exist** |
| `aa` | Artefact | **does not exist** (artifacts are `o`) |
| `am` | Material | **does not exist** |
| `sp` | Species | **does not exist** |
| `in` | Institutions | **does not exist** (real: `if`/`io`/`ia`/`ic`) |
| `nm` | Metrics | **does not exist** (real: `nc`/`na`/`no`…) |
| `cb` | Bibliographic | **does not exist** (container is `C`) |

**2. Two structural misreadings of CNEC 2.0.**
- `A` is the **Address** container, **not** "Artifacts/Objects" — so the `A → aa/am` branch is wrong at the root. Artifacts are lowercase `o` (`oa/oe/om/op/or`).
- Capital letters (`P/T/A/C`) mark **complex/embedded** spans, not a "capital-letter supertype" layer. The family is simply the first letter of the two-letter code (`g*`, `t*`, `o*`…).

**3. Only one archaeo type actually maps onto CNEC** — `LOCATION` → geographical `g`. `PERIOD` overlaps only for calendar dates (`ty`), not epochs ("Late Neolithic"); `ARTEFACT`/`CONTEXT`/`MATERIAL`/`SPECIES` have **no CNEC equivalent**. Confirms @motyc: *Location merges, Period is custom.*

**4. The alignment strategy is backwards (the key point).** NameTag 3 multitagset applies **output tagset masks** — every tagset keeps its own label inventory. So we register a **separate `archaeo` tagset** that coexists with CNEC; we do **not** force archaeology into `gc/aa/tp`. Any merging belongs at the **coarse output level only** (e.g. `LOCATION → LOC`), which our TEITOK output already supports via `@type` (CoNLL) + `@cnec` (fine code).

**5. Wrong base model for our language.** ArchaeoBERT is English; our pipeline runs Czech (`nametag3-czech-cnec2.0-240830`). Don't bind English ArchaeoBERT via `--hf_plm`. Use a multilingual PLM (XLM-RoBERTa — NameTag 3's multilingual backbone) and reuse ArchaeoBERT's annotation **guidelines**.

],

| `PERIOD` | `PER` | Dates, epochs, dating spans, ABR codes; drop leading "circa/after" and the word "period". | partial (dates ≈ `ty`) |

| `CONTEXT` | `CON` | Human-made features that can contain finds (moat, ditch, posthole); exclude natural/modern/over-general. | new |
| `MATERIAL` | `MAT` | What an artefact is made of (flint, bronze, brick); exclude metonyms & adjectives. | new |
| `SPECIES` | `SPE` | Animal/plant/human species; Latin + common name annotated separately. | new |

`PER` is deliberately renamed `PERIOD` to avoid clashing with the universal meaning of `PER` = *Person*. If we want to reuse ArchaeoBERT's annotated data verbatim (no relabeling), use the 3-letter variant instead: `["O","B-ART","I-ART","B-PER","I-PER","B-LOC","I-LOC","B-CON","I-CON","B-MAT","I-MAT","B-SPE","I-SPE"]`. Nested spans stay in the **data** as `B-MATERIAL|B-ARTEFACT` (handled by `--decoding=seq2seq`); no extra tagset entries needed.

### Solutions to consider
- **(A) Separate `archaeo` tagset via multitagset — recommended.** One shared XLM-R model serves CNEC + archaeo as separate endpoints; no code collisions; coarse mapping (`LOCATION → LOC`) keeps interoperability. Cost: build the labelled corpus + one `TAGSETS` / `--tagsets` entry.
- **(B) Remap into CNEC fine codes — avoid.** Fights the masking design, forces the collisions above, pollutes CNEC semantics. Keep only the coarse CoNLL-level mapping.
- **(C) Standalone archaeo-only model — fallback.** Clean labels and simplest, but loses the shared backbone and single-model serving.

<summary>Advanced Methodological Framework for Domain-Specific Named Entity Recognition in Archaeological Texts: Developing the NameTag 3 Training Routine</summary>

## **Introduction to the Semantic Enrichment Paradigm**

The ongoing development of computational pipelines for historical and archaeological document processing necessitates highly specialized natural language processing architectures capable of traversing complex textual topographies. Within the operational framework of the ATRIUM project, the semantic enrichment of text lines extracted from historical documents represents a critical technological milestone. The integration of Optical Character Recognition outputs into Natural Language Processing pipelines is foundational to the mid-project beta testing protocols defined under Work Packages 4 and 5, which seek to bridge raw document ingestion with advanced Web Annotation delivery mechanisms1. The natural language enrichment strategy currently utilizes a bifurcated approach. One trajectory employs constrained decoding through Large Language Models to map broad thematic vocabularies onto document structures, while the second trajectory requires the deployment of a highly deterministic, domain-specific sequence tagger for exact token-level extraction2.  
The developmental mandate outlined in the repository tracking infrastructure focuses explicitly on the latter: the formulation and execution of a training routine for a custom Named Entity Recognition model utilizing the NameTag 3 architecture3. While generalized models perform adequately on standard news wire corpora, the archaeological domain features a highly idiosyncratic lexicon comprising stratified contexts, localized topological descriptors, binominal biological taxonomies, and precise temporal markers3. To capture this intelligence, the project draws upon the foundational guidelines established by ArchaeoBERT-NER, aiming to adapt its English-centric token classification parameters for a multilingual, high-performance sequence tagger3.  
Recent advancements in the core NameTag 3 codebase mandate a comprehensive re-evaluation of optimal training guidelines. Repository updates have introduced critical modifications to tokenizer length resolution, dynamic learning rate decay structures, and language data dependencies, all of which directly influence hyperparameter configurations4. The subsequent analysis delineates an exhaustive methodological blueprint for data harmonization, annotation schema formalization, architectural configuration, and the execution of the training routine tailored specifically to the archaeological domain, leveraging the state-of-the-art capabilities of the updated NameTag 3 framework.

## **Evaluating Information Extraction Modalities in the ATRIUM Workflow**

To contextualize the necessity of a dedicated NameTag 3 model, it is imperative to examine the broader ingestion and processing pipeline. The data feeding into the semantic enrichment module originates from ALTO XML files containing discrete text lines2. This text has already undergone preliminary layout-aware extraction utilizing architectures similar to LayoutLMv3, followed by generative Optical Character Recognition correction via models such as GLM-4v-9b to mitigate baseline noise inherent in archival documents2. The language of each text chunk is verified using FastText to route it to the correct processing logic, establishing a highly structured, multilingual input stream2.  
The initial approach to semantic extraction explored the use of Large Language Models operating under constrained decoding paradigms. By injecting hierarchical archaeological thesauri into the system prompts of models like Qwen 2.5 14B or Mistral Nemo, the pipeline utilized libraries such as lmformatenforcer to strictly bind the output to predefined JSON schemas defined via Pydantic models2. This approach, while highly effective for assigning broad categorical labels and mitigating formatting hallucinations, exposed critical vulnerabilities when tasked with fine-grained token extraction. Iterative testing revealed that certain generative models exhibited severe categorization biases, often defaulting to irrelevant geographic locations when encountering administrative meta-text, or inappropriately forcing broad classifications onto highly specific architectural descriptions2.  
Furthermore, the computational overhead required to execute 14-billion-parameter models for every text line poses significant scalability challenges for massive archival datasets. While Large Language Models provide unmatched conceptual mapping capabilities, the precise, deterministic localization of multi-token entities within a string requires the mathematical rigidity of a dedicated sequence tagger2. NameTag 3, operating at either a base size of approximately 126 million parameters or a large size of 355 million parameters, achieves superior token-level accuracy while demanding a fraction of the inference compute, rendering it the optimal solution for the high-throughput demands of the ATRIUM semantic enrichment pipeline6.

## **Formalization of the Domain-Specific Annotation Schema**

The foundation of a high-performing Named Entity Recognition model is a rigorously defined, internally consistent annotation schema. The schema proposed for this developmental phase is heavily inspired by the guidelines established for ArchaeoBERT-NER3. Adapting this paradigm for the ATRIUM linguistic requirements involves defining distinct boundaries for six core entity types: Artefacts, Time Periods, Locations, Contexts, Materials, and Species3.  
A critical architectural decision highlighted in the developmental discussions is the selection between a flat entity schema, comprising several mutually exclusive named entity types, and a nested entity schema, featuring major named entity types with multiple embedded subtypes3. The decision directly dictates the mathematical decoding head utilized by NameTag 34. Given the foundational rules mapped out in the ArchaeoBERT guidelines, which largely separate materials from artefacts and species from artefacts, a flat, non-overlapping classification schema is the most mathematically stable starting point for the annotation effort3.  
The training data must be annotated using the IOB2 encoding format. In this structure, the O tag denotes tokens outside any relevant entity, the B- prefix marks the initial token of an entity type, and the I- prefix indicates subsequent tokens contained within the exact same entity span3. The NameTag 3 architecture requires strict adherence to IOB2 to function correctly, necessitating the conversion of legacy datasets prior to training8. The designated entity classes and their strict annotation boundary rules require exhaustive definition to ensure inter-annotator agreement and consistent algorithmic convergence.

### **Artefacts Extraction Parameters**

The Artefact classification encompasses physical objects discovered during excavation. The linguistic variance in describing archaeological finds ranges from singular nouns to highly complex noun phrases featuring multiple pre-modifiers and post-modifiers. The annotation process must capture the core object, whether it is a small ecofact like pollen or a massive vessel3. Structural building components unearthed during excavation, including beams, planks, and localized rampart debris, are explicitly categorized as artefacts within this schema3. Natural finds that serve as definitive archaeological evidence, such as iron ore deposits or index fossils, are also incorporated into this category3.  
The handling of adjectival modifiers presents a complex boundary alignment issue. Descriptive adjectives must be absorbed into the entity span to provide the model with maximal context. Consequently, the entirety of a phrase such as "rough-walled sherd" or "burnt wattle and daub" must be tagged sequentially3. However, a strict boundary exception applies to adjectives that denote the material composition of the object. For example, the token "metal" in the phrase "metal household goods" represents a boundary conflict with the separate Material category and is generally excluded from the Artefact tag to prevent overlapping semantic representations3.  
Overly broad, non-specific categorization terms are strictly excluded from the annotation process. Tokens forming generalized phrases like "find material", "artefact", "find complexes", or "archeobotanical material" dilute the model's precise localization capabilities and create ambiguity3. These terms lack the physical specificity required for robust indexing and must be tagged as outside the entity space.

### **Temporal Metadata and Time Periods**

The extraction of temporal metadata is critical for placing archaeological contexts within chronological timelines. The Time Period category exhibits significant morphological diversity, ranging from exact calendar years to broad historical epochs and named eras3.  
When specific calendar dates are present in the text, the extraction protocol mandates isolating only the year. For instance, in a string containing a full date sequence, the days and months are ignored, and only the specific numerical year is annotated as the beginning of the period3. For continuous time spans denoting a range, the surrounding prepositions and conjunctions are absorbed directly into the entity boundary. A phrase indicating a span from one specific century to another is tagged in its entirety, providing the sequence tagger with the structural markers of chronological range3.  
Relational modifiers that establish relative chronology present a distinct challenge. Preceding markers such as "after", "before", "circa", "around", or "approximately" are explicitly excluded from the entity boundary3. These words describe a relationship to the period rather than constituting the period itself. Formal historical periods, conversely, are fully annotated alongside their integral descriptors, such as the Late Medieval era or the Carolingian period. In these instances, the word "period" or "time" is included if it acts as a formal suffix to a named epoch, but generic references to a "period" preceding a chronological identifier are truncated3. Furthermore, the archaeological domain requires the unique inclusion of years contained within bibliographic citations present in the running text. However, alphanumeric project codes or archival identifiers containing year segments are systematically excluded to prevent the misclassification of administrative metadata as historical time3.

### **Spatial Localization and Geographic Contexts**

Spatial data in excavation reports encompasses a vast spectrum of geographic designations, from highly localized site coordinates to sweeping national boundaries. The Location tag targets geopolitical entities including municipalities, provinces, and countries3.  
A strict normalization rule applies to administrative prefixes and suffixes. Terms identifying the administrative status of a location, such as the word "Municipality" preceding a town name, are stripped from the annotation, leaving only the proper noun3. Full physical addresses, including street names, postal designations, and specific institutional locations like universities, are fully captured within the entity boundaries3. Prepositions indicating location, such as "in" or "at", along with the preceding localized segment, are grouped into a single contiguous entity to preserve the spatial relationship mapped in the text3.  
Exclusion criteria for the Location class are rigorous. Broad geographic generalizations, generic topographic features including rivers, seas, lakes, and highways, as well as raw numerical geographic coordinates, are omitted3. Directional prefixes are only included if they form an inseparable component of the official proper noun governing the region. Adjectives indicating a place of origin modifying another noun are similarly ignored to prevent classification bleed3.

### **Archaeological Contexts and Features**

In archaeological nomenclature, a "context" refers to a distinct, man-made physical feature or stratigraphical unit. These contexts frequently contain artefacts, though the presence of physical finds is not a prerequisite for their classification3.  
Features such as cesspits, moats, granaries, ditches, ring forts, and burial mounds are definitively classified as Contexts3. Structural remnants, including wall remains or structural postholes, are also included within this category, serving as critical spatial markers within an excavation topology3.  
The exclusion criteria for Contexts focus on separating human-made interventions from natural geology and modern infrastructure. Natural geological formations, such as dunes or peat layers, alongside basic soil typologies like sand or clay, are strictly excluded3. Modern infrastructural contexts, such as basements or contemporary garages, are similarly omitted to prevent false positive extraction in reports detailing excavations within modern urban environments3. Adjectival modifiers are typically stripped from the context noun unless they fundamentally alter the structural definition of the feature3.

### **Material Composition Analysis**

The Material entity is designed to capture the physical composition of an extracted artefact or an architectural feature. This tag operates in close proximity to the Artefact tag, requiring precise demarcation to avoid span overlap in a flat entity schema.  
The material is annotated only when it directly denotes the composition of an adjacent or implied artefact or structure. In descriptions of objects made of bone, flint, or bronze, the specific composition token is annotated3. Conversely, if the material noun functions syntactically as the artefact itself within the sentence structure—for example, a reference to "the glass" recovered from a trench—it receives the Artefact tag, not the Material tag3. Terms denoting construction materials applied to architectural features are also valid Material entities3. Adjectives detailing the state or condition of the material, such as "molten" or the specific tree type of a wood sample, are systematically stripped to preserve the foundational material classification3.

### **Biological Species and Taxonomic Classifications**

The Species tag isolates biological taxonomies, a crucial component for archaeobotanical and zooarchaeological analysis. This category requires strict handling of human remains and multi-word conceptual structures.  
References to human remains require careful boundary demarcation. In phrases discussing human bones, the physical remains are tagged as Artefacts, while the modifier indicating humanity is conceptually linked to the Species category3. However, generalized, philosophical, or broad historical references to humanity or human influence are strictly ignored by the tagging protocol3.  
In compound archaeological descriptions where an animal modifier is inseparable from the physical object it constitutes, the entire phrase acts functionally as an artefact. Therefore, the Artefact tag supersedes the Species tag3. When texts provide both colloquial terminology and scientific Latin binomial nomenclature consecutively, the tokens must be split into entirely separate entities. A sequence featuring an English or regional name followed immediately by its Latin equivalent requires an outside delimiter token between them to prevent the model from learning an artificially conjoined taxonomic representation3.

### **Synthesizing Entity Boundary Protocols**

Cross-category alignment rules apply uniformly across the entire dataset to ensure algorithmic consistency during the learning phase. Definite and indefinite articles leading an entity are excluded from the boundary unless they occur internally within a multi-word proper noun phrase3. Parenthetical text physically adjacent to or embedded within an entity string is absorbed into the annotation span only if it provides integral semantic modification to the core noun3. Entities conjoined by conjunctions such as "or" must be annotated as entirely separate spans, forcing the model to recognize discrete possibilities3. Tokens denoting non-specific quantities are universally excluded from all entity boundaries3.

## **Data Preprocessing and Format Harmonization**

The successful integration of the ALTO XML extraction pipeline with the NameTag 3 training routine demands rigorous data harmonization. The raw text lines extracted from historical documents must be structurally transformed into a format optimized for Transformer-based sequence labeling. NameTag 3 requires all training, development, and testing data to be encoded in UTF-8, formatted as vertical text files containing exactly two tab-separated columns8. The first column houses the isolated word form, while the second column houses the corresponding IOB2 annotation8. Datasets utilizing space-separated columns will cause immediate parsing failures and gradient calculation errors during data loading8.  
To leverage the deep contextual sequence modeling capabilities inherent in Transformer architectures, the data structure must clearly delineate both sentence and document boundaries. An empty line must seamlessly separate individual sentences within the corpus8. Furthermore, because archaeological site descriptions and historical contexts often span multiple consecutive sentences, enabling document-level context significantly improves the model's capacity for entity disambiguation. Document boundaries are programmatically marked using a distinct token row consisting of the string \-DOCSTART- mapped to an O tag8.  
When the underlying NameTag 3 training command invokes the split document context parameter, the architecture injects a sliding window of surrounding document text into the Transformer's attention mechanism. This allows the model to classify ambiguous tokens based on macroscopic thematic cues present in the broader paragraph, a capability that isolated sentence training lacks2.  
If the initial annotated archaeological dataset is encoded in the older, more permissive IOB format—where the first token of an entity is only marked with a beginning tag if it directly follows another entity of the identical type—it must be deterministically converted to the strict IOB2 format. The NameTag 3 repository provides the preprocessing/iob\_to\_iob2.py utility for this exact transformation, ensuring that every entity strictly initiates with a definitive beginning boundary marker8.  
The data processing pipeline commands required to normalize space-separated raw files into fully compliant NameTag formats execute a series of text manipulations, cutting irrelevant columns, replacing delimiters, and standardizing the sequence tags8.

## **Architectural Evolution: The NameTag 3 Paradigm**

Transitioning to NameTag 3 for the ATRIUM enrichment pipeline offers substantial architectural upgrades over earlier iterations, fundamentally altering the optimal approach to model training. The original NameTag 1 utilized a fast, robust feedforward neural network designed solely for flat named entity recognition11. NameTag 2 introduced deep learning contextualization by employing a Bidirectional Long Short-Term Memory (Bi-LSTM) layer resting upon frozen, pre-trained BERT contextualized word embeddings, allowing it to recognize both flat and nested entities12. While computationally efficient, freezing the lower Transformer layers severely limits a model's ability to adapt its foundational semantic representations to highly specialized, non-standard vernaculars.  
NameTag 3 discards the Bi-LSTM approach entirely in favor of full, end-to-end fine-tuning of Large Language Models4. The system attaches a mathematically specialized decoding head directly to the final hidden states of the Transformer block, optimizing the entire network down to the embedding layer6. The architecture natively supports both primary forms of entity extraction through distinct mathematical pathways.  
For corpora containing mutually exclusive, non-overlapping entities—as is intended for the flat archaeological tagset—NameTag 3 applies a standard softmax classification head over the individual token representations4. This flat decoding process assigns a definitive probability distribution to each token. Conversely, if an annotation schema dictates embedded entities of arbitrary depth, the architecture utilizes a complex sequence-to-sequence decoding head. This approach relies on the linearization of the entity structure, allowing the model to generate a sequence of opening and closing tags that naturally handle hierarchical relationships without collision4. The decoding parameter configuration during the training initialization must exactly match the structural logic of the finalized annotated dataset.  
Furthermore, NameTag 3 introduces the capability of multitagset learning6. The system acts as a single joint model capable of processing multiple languages, datasets, and disparate tagsets simultaneously, enabling profound cross-lingual and cross-domain transfer learning. By fine-tuning a model on combinations of the CoNLL, Universal NER, and OntoNotes tagsets alongside custom domains, the foundational representations learn highly generalized concepts of nominal structures before specializing13.

## **Codebase Modifications and Dependency Enhancements**

The GitHub repository hosting NameTag 3 is subject to continuous integration and optimization. Recent codebase modifications directly impact the execution stability and algorithmic convergence of the training routine, necessitating adjustments to the computational environment.  
A critical commit recently resolved a persistent issue regarding the maximum length handling of Hugging Face tokenizers when left undeclared4. In the processing of unsegmented ALTO XML outputs, text chunks generated by Optical Character Recognition can occasionally lack distinct punctuation markers, leading to exceptionally long, unbroken token sequences. This codebase enhancement ensures that the tokenizer dynamically truncates or intelligently handles these sequences without throwing fatal out-of-memory errors or out-of-bounds index exceptions during batch collation, ensuring continuous training stability4.  
Additionally, the developer environment has been updated to support explicit command-line arguments governing learning rate decay4. Previous iterations utilized rigid decay mappings tethered to the logging directory structure, offering limited flexibility. The introduction of specific decay variables and warmup epoch parameters allows the optimization landscape during fine-tuning to be smoothed significantly4. In deep Transformer fine-tuning, applying a rapid learning rate to a specialized dataset can induce catastrophic forgetting, where the pre-trained semantic weights are irretrievably distorted. Utilizing precise decay schedules mitigates this risk. Finally, the environmental requirements have been updated to mandate the language\_data package, a dependency strictly required for the accurate programmatic determination of language codes during cross-lingual mapping functions4.

## **Formulation of the Advanced Sequential Fine-Tuning Routine**

With the raw archival data structurally harmonized and the underlying architectural mechanics fully understood, the actual model training parameters can be mathematically formulated. The objective is to produce a state-of-the-art domain-specific sequence tagger that integrates efficiently into the overarching ATRIUM ecosystem without exceeding hardware constraints.

### **Foundation Model Selection and Regularization**

The selection of the underlying pre-trained language model dictates both the computational overhead of the training routine and the ultimate cross-lingual transfer capability of the inference engine. For tasks demanding high multilingual fluency—particularly relevant if the archaeological texts contain mixed-language archival citations, Latin taxonomic terms, and diverse geographic nomenclature—utilizing the 355-million-parameter xlm-roberta-large foundation model provides immense representational capacity6. If the target corpus is overwhelmingly restricted to a single language, such as Czech, deploying a monolingual base model comprising approximately 110 million parameters offers vastly superior computational speed and a smaller memory footprint while maintaining competitive evaluation metrics8.  
Given the inherent constraints on dataset size typical of highly specialized, newly annotated domain corpora, strict algorithmic regularization and careful gradient updates are required to prevent overfitting. A conservative batch size ranging between four and eight is highly recommended8. In the context of large Transformer fine-tuning, smaller batch sizes inject stochastic noise into the gradient descent process. This noise acts as a powerful empirical regularizer, forcing the model to generalize rather than memorize the limited training examples8. Furthermore, hard memory limitations, particularly when utilizing large parameter models alongside expansive document-level context windows, necessitate low batch sizes to prevent catastrophic Graphics Processing Unit memory exhaustion8.  
Transformer fine-tuning remains notoriously sensitive to learning rate selection. A highly conservative rate is standard for RoBERTa-based models to ensure the delicate contextual weights are adjusted smoothly without inducing exploding gradients8. If lower layers are initially frozen to stabilize the randomly initialized classification head, a slightly higher learning rate can be applied to the unfrozen head before unfreezing the entire network for holistic optimization16. Setting the maximum duration to a baseline of twenty epochs provides sufficient passes over the training distribution. NameTag 3 natively monitors validation loss on the development dataset and automatically caches the best-performing checkpoint, rendering the manual implementation of aggressive early stopping algorithms unnecessary8.

### **Multi-Tagset Transfer Learning Execution**

Instead of initializing training from scratch using an arbitrary pre-trained foundation model, the most effective methodology leverages NameTag 3's unique multitagset transfer learning capabilities6. This capability allows the newly initialized model to capitalize on named entity recognition features learned across dozens of other languages and standardized datasets.  
The officially distributed multilingual checkpoint has been rigorously pre-trained on seventeen languages across twenty-one distinct datasets, optimizing its internal representations for precise entity boundary detection13. By loading this specific checkpoint, the system bypasses the initial phase of learning what constitutes a basic noun phrase, beginning the training cycle already possessing a profound semantic understanding of named entities. To execute sequential fine-tuning on the archaeological dataset, the computational routine must load the multilingual checkpoint and explicitly define the new domain-specific tagset, overriding the default CoNLL or OntoNotes configurations8.  
Assuming the target entities are non-overlapping and the dataset has been mathematically normalized to a custom tagset designation, the configuration integrates the foundational model, the optimal learning rates, and the necessary document context windows into a single executable shell command3. The parameter defining the load checkpoint instructs the architecture to ingest the pre-trained weights, while the tagsets parameter signals the creation and initialization of a new classification head mapped exclusively to the custom archaeological vocabulary defined during the annotation phase. Empirical evidence accumulated across various NameTag computational tutorials consistently indicates that sequential fine-tuning methodologies yield statistically significant improvements in final F1 scores when compared to training foundation models from a state of total random initialization3.

## **Deployment and Paradata Provenance Tracking**

Following the culmination of the sequential fine-tuning process and the achievement of satisfactory evaluation metrics, the resulting model checkpoint must be permanently integrated into the broader ATRIUM data pipeline. The project mandates rigorous data traceability and operational transparency, utilizing dedicated provenance tracking scripts to record tool versions, execution cycles, and specific computational configurations2. The NameTag 3 inference engine must log its final extractions in a highly structured schema compatible with this system.  
NameTag 3 offers versatile avenues for deployment, bypassing the need for complex internal API wrapping if configured correctly within the host environment4. For immediate, synchronous integration within the existing Python layout—running directly alongside the FastText verification and ALTO processing scripts—the native Python client can be imported or invoked directly via standard subprocess calls4. This allows the output to be programmatically manipulated and injected straight into the required JSON payloads.  
Alternatively, to isolate the heavy computational load of the Transformer and facilitate asynchronous pipeline architecture, the trained model can be hosted using the NameTag 3 Server setup. The REST Web Service is instantiated by passing the required initialization arguments: the model name, the directory containing the compiled custom checkpoints, the custom archaeological tagset, and any appended acknowledgments4. Client nodes distributed throughout the ATRIUM pipeline can subsequently process vast arrays of ALTO text via continuous HTTP requests. This microservice approach prevents context window exhaustion and systemic GPU memory bottlenecks that frequently afflict architectures attempting concurrent Large Language Model operations on single nodes2.  
By leveraging the recent tokenizer stability updates, incorporating dynamic learning rate decay parameters, and utilizing the advanced multitagset transfer capabilities intrinsic to NameTag 3, this methodological framework guarantees the deployment of a highly performant, resilient, and precise Named Entity Recognition system. This system will directly satisfy the semantic enrichment milestones, transforming raw archival character strings into structured, quantifiable historical intelligence.
