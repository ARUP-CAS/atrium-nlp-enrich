# Plan — TEITOK XSD Validation Output Contract (issue #28)

Repo: `ufal/atrium-nlp-enrich` · Branch: `feature/teitok-xsd-validation-28`

## Context

Issue [\#28](https://github.com/ufal/atrium-nlp-enrich/issues/28) identifies a critical missing safety net: while `atrium-translator` rigorously validates its AMCR output, `nlp-enrich` currently blindly trusts its generated TEITOK XML. If malformed XML slips through, it silently breaks downstream search indexes and visualizers, ultimately poisoning the LINDAT dataset release.

The resolution treats XSD validation as a **formal output contract**. Rather than just bolting a quick `xmllint` command to the end of `api_4_stats.sh`, we are building a reusable validator, vendoring the authoritative schema for reproducibility, and enforcing a hard pipeline gate *before* any packaging occurs. This mirrors the strict data classification and quality scoring logic already established for ALTO and TEITOK processing, ensuring the same level of integrity for structural XML conformance. 

**Decisions (confirmed via strategy):**
1. **Scope:** All generated `.teitok.xml` files must be validated. The pipeline must fail if even one document is malformed.
2. **Schema Management:** The official TEITOK schema will be vendored (pinned) in the repository to ensure network-free, reproducible validation during local development and CI.
3. **Integration:** A dedicated script (`api_util/validate_teitok_xml.sh`) will handle the validation logic, which `api_4_stats.sh` will call right before dataset packaging.

## Approach

Four targeted updates are required to establish this contract, keeping the logic modular and leveraging the existing centralized GitHub Actions workflow templates.

### 1. `schemas/teitok/` — The Pinned Output Contract
Create a dedicated directory to house the official schema. 
- Vendor `teitok.xsd` (and any imported sub-schemas) directly into this folder.
- Add a `README.md` documenting the schema's exact provenance: source URL, pinned Git commit/version, and retrieval date. This ensures the LINDAT dataset's structural contract is permanently auditable.

### 2. `api_util/validate_teitok_xml.sh` — The Reusable Validator
A simple, dependency-light shell script using `libxml2-utils`. 
- **Input:** Takes the target output directory as `$1`.
- **Execution:** Iterates over `*.teitok.xml` in the directory, running `xmllint --noout --schema schemas/teitok/teitok.xsd "$xml_file"`.
- **Output:** Must retain and print the specific document filename alongside the `xmllint` diagnostics if a failure occurs (e.g., `[FAIL] CTX000000003.teitok.xml`). 
- **Exit:** Returns `0` if all documents pass, and `1` if *any* document fails.

### 3. `api_4_stats.sh` — The Pipeline Gate
Insert the validation call strictly *after* TEITOK compilation and post-processing, but *before* the final dataset packaging.
```bash
echo "Validating TEITOK XML output contract..."
if ! bash api_util/validate_teitok_xml.sh "$OUTPUT_DIR"; then
    echo "FATAL: Pipeline halted due to schema violations." >&2
    exit 1
fi
```

### 4. `data_samples/TEITOK/` & CI Updates — Enforcement

* **Fixtures:** Add `CTX_valid.teitok.xml` and an intentionally broken `CTX_invalid.teitok.xml` (e.g., containing an unexpected element) to the test data.
* **CI Workflow (`.github/workflows/api-contract.yml`):** Update the centralized workflow template to explicitly `sudo apt-get install -y libxml2-utils` during setup. Add a step that runs the validator against the *invalid* fixture and asserts that it correctly returns a non-zero exit code, proving the gate actively catches errors.

### Reuse (don't reinvent)

Utilize the established logging paradigms in `api_util/api_common.sh` for reporting validation progress. Rely on the existing `xmllint` paradigm established in other ATRIUM repositories rather than introducing new Python-based XML parsers just for validation. Leverage the centralized GitHub Actions CI/CD infrastructure to handle the dependency provisioning.

## Verification

1. **Install Dependencies:** Ensure `xmllint` is available locally (`apt-get install libxml2-utils` or `brew install libxml2`).
2. **Schema Sanity Check:** Run `xmllint --noout --schema schemas/teitok/teitok.xsd data_samples/TEITOK/CTX000000001.teitok.xml` manually to ensure the vendored schema works.
3. **Validator Script Smoke Test:**
   * Run `bash api_util/validate_teitok_xml.sh data_samples/TEITOK/` on the valid fixtures. Expect clean `[OK]` logs and `exit 0`.
   * Introduce the invalid fixture and run again. Expect an explicit `[FAIL]` log with line-number diagnostics and `exit 1`.
4. **End-to-End Pipeline:** Run `api_4_stats.sh` locally. Verify that the new validation step echoes to stdout, processes the files, and successfully moves on to packaging.
5. **CI Enforcement:** Push to the feature branch. Verify that the GitHub Action installs `libxml2-utils`, successfully runs the negative test case against the invalid fixture, and ultimately passes the overall integration build.
